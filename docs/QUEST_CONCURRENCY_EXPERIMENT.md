# 퀘스트 승인 동시성·FCM 지연 측정 결과

측정일: 2026-11-05 · 이슈: #218 · 기준 커밋: `f0cc989` (development 배포 커밋) · 작업 트리 변경: 4건 (모두 추적되지 않은 테스트·도구·측정 파일, `src/main` 변경 없음)

## 1. 목적

`QuestReviewService.approve`는 행 잠금, `PENDING` 조건부 갱신, 멱등 키로 동시 승인과 중복 지급을 막도록 설계했다. 하지만 요청이 실제로 동시에 들어오는 테스트는 없었다.
이 측정은 두 가지를 확인한다. 동시 요청에서 돈과 상태가 맞는지, 그리고 승인 트랜잭션 안의 동기 FCM 호출이 같은 부모 지갑을 쓰는 다른 요청을 얼마나 기다리게 하는지다.

## 2. 조건

- 환경: Windows 11, 논리 코어 12, 메모리 64GB, JDK 17.0.10, MySQL 8.0.33 (로컬 PC, `localhost:3306`)
- 판정 테스트: FCM 0ms, 풀 20, 시나리오별 30회
- 측정: 풀 {20, 10} × FCM {0, 100, 300}ms, 준비 3회 제외 30회, 동시 요청 15건(승인 5 · 용돈 5 · 충전 5)
- FCM은 가짜 객체(지연 주입)다. 실제 네트워크 호출은 없다.
- 드라이버: `com.mysql.cj.jdbc.Driver` (log4jdbc 제외)

## 5. 가설 판정

주 지표는 CHARGE의 p95 증가분이다. 충전은 알림을 보내지 않아 잠금·커넥션 대기만 반영한다.
ALLOWANCE는 커밋 뒤 자기 알림 FCM도 기다리므로 보조 지표로만 쓴다.

- **잠금 가설: 맞음.** 충전 p50은 FCM 지연과 관계없이 7~9ms로 그대로인데, p95는 풀 20에서 25ms → 331ms로 FCM 지연(300ms)만큼 늘었다. 승인과 같은 순간에 부모 지갑을 잡으려던 충전이, 승인이 FCM 응답을 기다리며 쥐고 있는 지갑 잠금을 그만큼 기다린 것이다. 회차당 잠금 대기 시간 합도 193ms → 2,050ms로 늘었다.
- **커넥션 고갈 가설: 부분적으로 맞음.** 풀 10에서는 커넥션을 기다린 스레드가 최대 4~5개였고(풀 20은 0), 승인 p95가 641ms로 FCM 지연의 약 2배가 됐다. 충전 p95는 풀 10과 20이 비슷했다(334ms, 331ms). 동시 요청 15건이 풀 10보다 많아서 생긴 대기이며, 관련 없는 요청까지 막히는지는 이 실험 범위(같은 부모 지갑 요청만)로는 판단할 수 없다.

## 6. 한계

- 로컬 PC 한 대의 수치다. 운영 성능으로 읽지 않는다.
- MySQL 잠금 지표는 서버 전역 값이다.
- FCM 지연은 가정값(0/100/300ms)이다. 운영에서 잰 용돈 지급 응답(2026-11-05, 10건)은 대부분 390~560ms였고 `/health`는 약 76ms였다. 운영 FCM 지연은 300ms보다 클 수 있다.
- 서비스 계층 측정이라 HTTP·보안 필터·Tomcat 시간은 포함하지 않는다.
- 지연 작업에는 승인 5건 동시가 들어 있어 실제 사용보다 경합이 크다. 지연 표는 성공한 요청만 센다.
